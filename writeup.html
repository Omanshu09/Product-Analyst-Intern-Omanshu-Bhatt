Task 1 — Where the docs and the data disagree

  1. Monetary values aren't consistently integer cents. The docs say every amount is an integer in the smallest unit (5470 = $54.70). Only ord_1006 in orders_page2.json breaks this: its subtotal/tax/shipping/total (44.0, 3.63, 5.99, 53.62) are decimal dollars. A client dividing every total by 100 reads this order as $0.54 instead of $53.62 — a silent ~$53 undercount, no error thrown.
    This is the worst of the five — it doesn't error, return a null, or 404; it feeds a wrong number straight into a sum. The other four at least surface something a defensive reader would notice (unexpected value, missing field, mismatched status code).
  2. refunded isn't a documented status. The docs list pending/shipped/delivered/cancelled; ord_1003 returns refunded. Code written strictly against the docs has no branch for it, so a $102.33 order can be counted as live revenue.
  3. customer.email isn't always present. Docs say "always present," but ord_1005 returns email: null (guest checkout). Anything keying off email — dedup, outreach, invoicing — breaks or mis-groups that customer.
  4. A missing order returns 200, not 404. Docs promise a 404 when an order doesn't exist; order_ord_9999.json, the response for non-existent ord_9999, came back HTTP 200 with {"order": null}. Status-code handling won't catch this; the client reads fields off null and crashes.
  5. has_more contradicts next_cursor. orders_page1.json says has_more: false, yet returns a real next_cursor. A client trusting has_more, as instructed, stops after page 1 and silently misses the two orders on page 2.

Bug report

Title: Order amounts inconsistently formatted — decimal dollars instead of integer cents

Where: GET /v1/orders response, order ord_1006 (page 2, starting_after=cur_8f2a19bd)

What happens: subtotal/tax/shipping/total are 44.0, 3.63, 5.99, 53.62 — decimal dollars. Every other order on both pages uses integer cents (e.g. ord_1001.total = 5470 for $54.70), matching the docs' worked example.

What should happen: All four fields should be integer cents — 4400, 363, 599, 5362 — matching every other order and the documented format.

Why it matters: A consumer following the documented contract (divide by 100) silently computes $0.5362 instead of $53.62. Nothing errors or falls out of range — the number is just wrong — and this directly caused the TICKET-4502 discrepancy.

Suggested first step: Check what wrote this record for a missed × 100 conversion, or a divergent code path for edge-case orders — ord_1006 sits next to guest order ord_1005, which is also anomalous (email: null), so the same pipeline may be worth auditing end to end.
